## 핵심 원칙 요약

- **바운디드 컨텍스트 중심 모듈화**: 최상위 구조는 기술 계층이 아닌 바운디드 컨텍스트를 기준으로 나누며, 각 컨텍스트는 공개 인터페이스 모듈(`<컨텍스트>-api`)과 내부 구현 모듈(`<컨텍스트>-core`)로 구성합니다.
- **구현 은닉과 단방향 의존**: 외부 컨텍스트에는 `-api` 모듈만 노출하며, 서로 다른 컨텍스트의 `-core` 모듈 간 직접 의존은 허용하지 않습니다.
- **서브도메인 특성에 맞춘 내부 구조**: 외부에 노출하는 계약 형태는 모든 컨텍스트가 동일하게 맞추되, `-core` 내부 아키텍처(헥사고날 또는 레이어드)는 각 서브도메인의 복잡도와 외부 의존 특성에 따라 선택합니다.
- **조립 모듈(`apps/*`)의 역할 분리**: `apps/*`는 필요한 컨텍스트 모듈들을 조합해 실행 프로세스로 띄우는 조립 모듈이며, HTTP 요청 인증과 화면용 데이터 조합(`composition`)만 직접 담당합니다.
- **느슨한 컨텍스트 간 결합**: 컨텍스트 간 동기 조회는 향후 원격 호출 전환을 고려해 설계하며, 상태 변화에 따른 후속 처리는 Outbox와 Kafka를 통한 비동기 이벤트로 전달합니다.
- **트랜잭션 및 데이터 격리**: 하나의 트랜잭션에는 단일 컨텍스트의 쓰기 작업만 포함합니다. 데이터베이스 역시 컨텍스트마다 독립된 스키마를 사용하며, 다른 컨텍스트의 스키마를 SQL로 직접 참조하지 않습니다.

## 아키텍처 규칙의 자동 검증

문서에 정의된 규칙 중 정적 분석으로 검증할 수 있는 항목은 Gradle 모듈 의존성 제약과 ArchUnit 테스트를 통해 빌드 시점에 강제합니다.

- 공통 검증 규칙은 `platform/architecture-rules` 모듈에 정의되어 있으며, 각 컨텍스트(예: `MemberArchitectureTest`)와 실행 앱(`apps/api`의 `ArchitectureTest`)의 테스트 코드에서 이를 호출해 검증합니다.
- 상세 구현 방식과 규칙 자체에 대한 검증 방법은 [02-context-architecture.md](02-context-architecture.md)의 `ArchUnit` 절에 정리되어 있습니다.
- 설계 변경으로 인해 아키텍처 규칙을 수정해야 할 때는 테스트를 우회하지 않고 이 문서와 ArchUnit 테스트를 함께 변경합니다.
