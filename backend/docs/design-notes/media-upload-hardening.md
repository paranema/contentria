# 미디어 업로드 강화 설계

이미지 업로드 기능에서 발생할 수 있는 보안 위협과 이를 방어하기 위한 다층 보안 체계 설계 배경을 기록합니다.

> [!NOTE]
> 구체적인 업로드 API 사양과 수치 기준은 [contexts/media/01-rules.md](../contexts/media/01-rules.md)를 참고합니다.

## 보안 위협 및 방어 요약

| 보안 위협 | 대응 방어선 | 적용 상태 |
|---|---|---|
| 대용량 파일 업로드로 인한 스토리지 고갈 | 파일 크기, 일일 회원별 용량, 글당 이미지 개수 제한 | 적용 완료 |
| 스크립트가 포함된 위장 파일 업로드 (XSS) | 파일 앞부분 시그니처(Magic Bytes) 검증 | 적용 완료 |
| 사진 메타데이터(EXIF)를 통한 위치·기기 정보 유출 | JPEG 이미지 재인코딩을 통한 메타데이터 파기 | 적용 완료 |
| 브라우저의 MIME 타입 자동 추측 실행 | `X-Content-Type-Options: nosniff` 응답 헤더 적용 | 부분 적용 (Next.js 적용, 스토리지 도메인 보류) |

## 업로드 용량 제한

### 문제 정의

한 회원이 무제한으로 업로드를 수행하여 스토리지 비용을 폭증시키거나 서비스 가용성을 해치는 서비스 거부 공격을 방지해야 합니다.

### 적용 규칙

| 제한 항목 | 기준값 | 검증 위치 |
|---|---|---|
| 단일 파일 크기 | 10MB 이하 | `Media.prepare` (도메인 엔티티) |
| 회원별 일일 업로드 총량 | 100MB 이하 | `ImageUploadService.prepare` (애플리케이션) |
| 글 1개당 첨부 이미지 수 | 20개 이하 | `PostImageLinks.MAX_IMAGES` (출판 컨텍스트) |

일일 업로드 누적량은 당일 준비된 업로드 레코드의 합계를 데이터베이스에서 조회하여 검증합니다.

### 속도 제한 검토

단시간 업로드 폭주를 막기 위한 요청 횟수 제한(Rate Limiting)은 현재 보류 상태입니다. 향후 다중 인스턴스 확장에 맞춰 Redis 기반 분산 토큰 버킷 방식 도입을 검토할 예정입니다.

## 파일 시그니처 검증

### 문제 정의

클라이언트가 전송하는 `Content-Type` 헤더나 파일 확장자는 위조가 가능합니다. 악의적인 사용자가 HTML이나 자바스크립트 코드가 담긴 파일을 `image/jpeg`로 속여 업로드하고, 이를 사용자가 열람할 때 브라우저에서 실행되도록 유도하는 저장형 XSS 공격을 차단해야 합니다.

### 검증 방식 비교

| 검증 방식 | 장점 | 단점 | 채택 여부 |
|---|---|---|---|
| 파일 확장자 검사 | 구현이 단순하고 빠릅니다. | 확장자 변조(`.html` → `.jpg`) 시 무력화됩니다. | 미채택 |
| 파일 전체 디코딩 | 이미지 정합성을 완벽하게 보장합니다. | 메모리 사용량이 많고 처리 속도가 느립니다. | 미채택 |
| **파일 헤더 12바이트 검사** | **빠른 속도로 파일 위장을 효과적으로 탐지합니다.** | **두 형식으로 동시 해석되는 파일(폴리글랏)은 탐지하지 못합니다.** | **채택** |
| Apache Tika 라이브러리 | 다양한 형식 판별이 가능합니다. | 단순 이미지 검증 목적에 비해 라이브러리가 무겁습니다. | 미채택 |

### 적용 규칙

1. **클라이언트 1차 사전 검증**: 브라우저에서 파일을 읽어 앞 12바이트 매직 넘버를 검증하고, 일치하지 않으면 업로드를 즉시 중단합니다 (`frontend/src/features/media/upload/uploadImage.ts`).
2. **서버 2차 정밀 검증**: 업로드 완료 시점(`complete`)에 스토리지에서 파일 앞부분을 읽어 허용된 형식(JPEG, PNG, WebP, GIF)의 시그니처와 실제 크기를 최종 검증합니다 (`ImageFormat.matches`, `ImageUploadService.complete`).
3. **위반 파일 즉시 삭제**: 검증 실패 시 DB 레코드와 스토리지 파일을 즉각 파기하여 서비스에 노출되지 않도록 처리합니다.

## 메타데이터 제거

### 문제 정의

카메라나 스마트폰으로 촬영된 JPEG 원본 이미지에는 EXIF(Exchangeable Image File Format) 데이터가 포함되어 있습니다. 여기에는 촬영 GPS 좌표, 기기 모델명, 촬영 일시 및 자르기 전 원본 미리보기(Thumbnail) 등이 포함되어 있어 사용자의 사생활이 침해될 위험이 있습니다.

### 처리 방식 비교

| 처리 방식 | 특징 | 채택 여부 |
|---|---|---|
| 메타데이터 파서 라이브러리 | 원본 픽셀을 유지하나 모든 세부 태그를 누락 없이 제거하기 어렵습니다. | 미채택 |
| CDN 자동 최적화 서비스 | 별도 백엔드 코드가 불필요하나 외부 유료 서비스 의존성이 발생합니다. | 미채택 |
| **JDK ImageIO 재저장** | **픽셀 데이터만 디코딩 후 새 파일로 다시 인코딩하므로 모든 메타데이터가 완전히 소멸합니다.** | **채택** |

### 적용 규칙

- **JPEG 재인코딩**: 업로드 완료 처리 시 `ImageIoCleaner`를 통해 이미지를 픽셀 단위로 디코딩한 뒤 품질 0.9로 재압축하여 저장합니다. 이 과정에서 EXIF, IPTC, XMP 메타데이터가 완전히 제거됩니다.
- **기타 형식 보존**: PNG, WebP는 민감 메타데이터가 포함되는 사례가 드물고, GIF는 재인코딩 시 애니메이션 프레임이 손실되므로 원본 바이트를 유지합니다.

## 보안 응답 헤더

### 문제 정의

스토리지에 저장된 이미지가 공개 CDN 도메인을 통해 제공될 때, 브라우저가 응답 헤더의 MIME 타입을 무시하고 파일 내용을 임의로 추측(MIME Sniffing)하여 악성 스크립트로 실행하는 위험을 방어해야 합니다.

### 적용 규칙

- `X-Content-Type-Options: nosniff`: 브라우저가 선언된 MIME 타입 외에 임의로 파일 내용을 추측 실행하지 못하도록 강제합니다. (현재 Next.js 앱 응답에 적용되어 있으며, R2 직접 서빙 도메인 적용은 인프라 구성 시 반영 예정입니다.)
- `Referrer-Policy: strict-origin-when-cross-origin`: 외부 사이트 자원 요청 시 불필요한 경로 정보가 누출되지 않도록 차단합니다.

## 다층 방어 구조

미디어 업로드 파이프라인의 각 단계별 방어 흐름은 다음과 같습니다.

```
업로드 시작
  ├─ [브라우저] 확장자, 크기 및 매직 바이트 사전 검증
  ├─ [브라우저] Canvas 기반 재인코딩 (클라이언트 레벨 메타데이터 1차 파기)
  │
  ├─ [업로드 준비] 형식 유효성 확인, 파일 크기(10MB) 및 회원별 일일 한도(100MB) 검증
  ├─ [스토리지 전송] 사전 서명된 Presigned URL을 통해 지정된 파일 규격으로만 수신
  │
  ├─ [업로드 완료] 서버 사이드 매직 바이트 및 크기 정밀 검증 (실패 시 즉시 파일 삭제)
  ├─ [업로드 완료] ImageIO 재인코딩을 통한 EXIF 메타데이터 영구 파기
  │
  ├─ [게시글 저장] 본문 내 첨부 이미지 최대 20개 제한 검증
  └─ [클린업 배치] 미완료 업로드(24시간) 및 미참조 고아 파일(7일) 자동 정리
```
