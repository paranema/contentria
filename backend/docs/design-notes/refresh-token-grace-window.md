# 리프레시 토큰 동시 갱신 설계

동일한 리프레시 토큰으로 동시에 토큰 재발급 요청이 인입될 때 발생하는 경쟁 상태(Race Condition)와 이에 대한 방어 설계 배경을 기록합니다.

## 동시 갱신 충돌 문제

리프레시 토큰 회전(RTR) 정책에 따라 리프레시 토큰은 갱신 시마다 즉시 폐기되고 새로운 토큰으로 교체됩니다.

이때 동일한 세션의 토큰으로 갱신 요청이 거의 동시에 여러 건 도착하면 다음과 같은 문제가 발생합니다:
1. 가장 먼저 도착한 요청이 토큰을 사용하고 새 토큰을 발급받습니다.
2. 뒤이어 도착한 요청은 이미 데이터베이스에서 삭제된 이전 토큰을 전달하게 되므로 `401 Unauthorized`를 응답받습니다.
3. 클라이언트는 유효 기간이 남아 있음에도 불구하고 인증 실패로 판단하여 사용자를 강제 로그아웃 처리합니다.

이러한 동시 갱신은 브라우저에서 여러 탭을 동시에 열거나, 화면 이동 시 병렬 API 호출 및 프리페칭(Prefetching)이 발생할 때 빈번하게 유발됩니다.

## 현재 대응 아키텍처

현재 시스템은 백엔드 복잡도를 최소화하기 위해 프론트엔드 계층에서 동시 요청을 묶어서 처리합니다.

| 계층 | 역할 및 처리 방식 | 관련 코드 |
|---|---|---|
| 프론트엔드 프록시 | 진행 중인 갱신 요청(`inflightRefresh`)이 존재할 경우 동일 토큰의 후속 요청을 기존 요청에 결합하여 결과를 공유합니다. | `frontend/src/proxy.ts` |
| 프론트엔드 서버 액션 | 화면 이동 프록시에서만 갱신을 수행하고, Server Action에서 401 수신 시 직접 갱신하지 않고 로그인 경로로 안내합니다. | `frontend/src/shared/api/apiServer.ts` |
| 백엔드 서비스 | 유예 기간 없이 데이터베이스 해시 조회 후 즉시 이전 토큰을 삭제하고 신규 토큰을 발급합니다. | `SessionService.refresh` |

## 잠재적 한계

현재 단일 인스턴스 기준의 프론트엔드 메모리 맵(`inflightRefresh`) 방식은 다음과 같은 환경에서 한계가 존재합니다.

- **프론트엔드 다중 인스턴스 환경**: 클러스터 환경에서 인스턴스 간 요청이 분산될 경우 메모리 결합이 동작하지 않아 뒤늦게 도착한 요청이 실패할 수 있습니다.
- **쿠키 반영 지연**: 앞선 갱신의 결합이 해제된 직후, 브라우저가 새 쿠키를 저장하기 전에 발송된 이전 요청이 백엔드에 도착하면 거부될 수 있습니다.

## 유예 구간 도입 방안

위의 한계로 인해 사용자 로그아웃 이슈가 가시화될 경우 백엔드에 유예 구간(Grace Window)을 도입합니다.

### 동시성 제어 방식 비교

| 제어 방식 | 장점 | 단점 | 평가 |
|---|---|---|---|
| 낙관적 락 (`@Version`) | 표준 JPA 기반으로 구현이 간단합니다. | 충돌한 후속 요청은 여전히 예외가 발생하여 사용자가 로그아웃됩니다. | 부적합 |
| 단순 비관적 락 (`FOR UPDATE`) | DB 레벨에서 요청을 순차 대기시킵니다. | 앞선 트랜잭션이 토큰을 삭제하므로 대기 후 실행된 요청은 대상을 찾지 못합니다. | 부적합 |
| Redis 분산 락 | 다중 백엔드 인스턴스 전반에 걸쳐 안전합니다. | 추가 인프라 구축 및 네트워크 왕복 지연이 발생합니다. | 보류 |
| **비관적 락 + 인메모리 캐시** | **트랜잭션 대기 중 앞선 트랜잭션이 발급한 신규 토큰을 캐시에서 즉시 반환합니다.** | **백엔드 다중화 시 인스턴스별 캐시 동기화가 필요합니다.** | **권장** |

### 권장 구현 구조

```
요청 1 (T1): SELECT ... FOR UPDATE (이전 토큰 해시) -> [행 잠금 획득]
요청 1 (T1): 새 토큰 발급, 캐시에 매핑 저장 (이전 토큰 해시 -> 새 토큰 정보, TTL 10초)
요청 1 (T1): DB COMMIT 및 행 삭제 -> [잠금 해제]

요청 2 (T2): SELECT ... FOR UPDATE (이전 토큰 해시) -> [T1 완료 후 진입, 행 없음]
요청 2 (T2): 인메모리 캐시 조회 -> 10초 유예 구간 내 매핑된 새 토큰을 확인하여 정상 응답 반환
```

- **캐시 생명주기**: 유예 시간은 네트워크 지연 및 클라이언트 쿠키 반영 시간을 고려하여 약 10초로 설정합니다.
- **액세스 토큰 재생성**: 액세스 토큰은 발급 시각과 만료 시점의 정합성을 위해 캐시하지 않고 요청마다 새로 생성하여 서명합니다.

## 제외 범위

유예 구간 경과 후 이전 토큰이 재전송되는 경우는 토큰 탈취 및 재사용 공격으로 간주하여 해당 계정의 모든 활성 세션을 즉시 무효화하는 침해 대응 정책은 별도 보안 기능으로 분리하여 다룹니다.
