# 바운디드 컨텍스트

[01-domain-overview.md](01-domain-overview.md)의 도메인 전제 조건과 [02-ubiquitous-language.md](02-ubiquitous-language.md)에 정의된 용어를 바탕으로 바운디드 컨텍스트의 경계와 책임을 정의합니다.

## 개요

### 컨텍스트 분리 기준

애그리거트는 단일 트랜잭션 내에서 불변식(일관성)을 보장하는 경계이고, 바운디드 컨텍스트는 동일한 도메인 모델과 유비쿼터스 언어가 통용되는 경계입니다. 따라서 **바운디드 컨텍스트는 단일 애그리거트 단위가 아니며**, 하나의 컨텍스트 안에 여러 애그리거트가 존재할 수 있습니다([배경 참고](#도메인-단위-컨텍스트-구성)).

여러 도메인 개념을 하나의 컨텍스트로 묶을지, 별도의 컨텍스트로 분리할지는 다음 세 가지 기준으로 판단합니다.

| 판단 기준                 | 핵심 질문                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------- |
| 언어의 일관성             | 동일한 단어가 동일한 의미로 사용되는가?                                                     |
| 함께 바뀌는 비즈니스 규칙 | 하나의 유스케이스에서 여러 애그리거트가 즉시 일관되게(단일 트랜잭션으로) 변경되어야 하는가? |
| 변경의 주체와 이유        | 동일한 행위자가 동일한 비즈니스 목적을 위해 변경하는가?                                     |

새로운 기능이나 개념이 추가될 때는 우선 기존 컨텍스트 내부의 애그리거트나 하위 모델로 배치를 검토하고, ① 기존 컨텍스트와 동일한 단어를 전혀 다른 의미로 정의해야 하거나, ② 변경 주체와 비즈니스 목적이 뚜렷이 다르거나, ③ 강한 트랜잭션 일관성 없이 비동기 이벤트 통지만으로 충분할 때만 별도 컨텍스트로 분리합니다.

### 컨텍스트 목록

위 기준에 따라 도출한 6개 바운디드 컨텍스트입니다. 영문 식별자는 실제 코드의 컨텍스트 디렉터리 이름 및 설계 문서 폴더 이름으로 동일하게 사용됩니다.

| 컨텍스트 | 영문 식별자    | 핵심 책임                                                       | 주요 애그리거트                                                      | 서브도메인 분류   |
| -------- | -------------- | --------------------------------------------------------------- | -------------------------------------------------------------------- | ----------------- |
| 회원     | `member`       | 회원가입, 인증, 계정 상태 관리, 프로필 관리                     | `Account` (내부 엔티티·VO: `Credential`, `Role`), `Profile`          | 일반 (Generic)    |
| 출판     | `publishing`   | 블로그 개설, 카테고리 관리, 게시글 작성 및 발행                 | `Blog`, `CategoryTree` (내부: `Category`), `Post` (내부: `PostSlug`) | 핵심 (Core)       |
| 상호작용 | `interaction`  | 블로그 구독, 댓글 작성, 게시글 좋아요                           | `Subscription`, `Comment`, `Like`                                    | 지원 (Supporting) |
| 미디어   | `media`        | 이미지·영상 업로드, 메타데이터 정제, HLS 변환, 미사용 파일 정리 | `Media`, `Video`                                                     | 지원 (Supporting) |
| 분석     | `analytics`    | 방문 기록 수집, 조회수 산출, 일별 통계 집계                     | `Visit`, `DailyStatistics`                                           | 지원 (Supporting) |
| 알림     | `notification` | 타 컨텍스트에서 발생한 도메인 이벤트를 회원에게 알림            | `Notification`                                                       | 일반 (Generic)    |

## 컨텍스트별 책임

### 소유 범위

각 컨텍스트가 직접 소유하는 데이터·규칙과, 화면상 함께 보이더라도 다른 컨텍스트가 소유하는 영역을 명확히 구분합니다.

| 컨텍스트 | 직접 소유하는 데이터·규칙                                                         | 소유하지 않는 것 (실제 소유 컨텍스트)                                                                         |
| -------- | --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------- |
| 회원     | 계정, 자격증명, 권한, 계정 상태, 표시 이름, 프로필 사진                           | 블로그 소유 관계 (출판)                                                                                       |
| 출판     | 블로그 및 소유자 식별자, 카테고리 트리 구성, 게시글 본문·상태, 마크다운 본문 형식 | 조회수 (분석), 좋아요 수 (상호작용), 작성자 표시 이름·프로필 사진 (회원), 미디어 원본·변환 파일 저장 (미디어) |
| 상호작용 | 구독 관계, 댓글, 좋아요, 게시글별 좋아요 수                                       | 게시글 공개 여부 (출판), 댓글 작성자의 표시 이름·사진 (회원)                                                  |
| 미디어   | 파일 메타데이터, 스토리지 저장 경로, 업로드·변환 상태, 파일과 게시글의 연결 정보  | 마크다운 본문 내에서 어떤 이미지 파일을 참조하는지 파싱·판단하는 규칙 (출판)                                  |
| 분석     | 방문 로그, 조회수, 순방문자 수, 일별 집계 통계                                    | 인기 게시글의 제목과 슬러그 (출판)                                                                            |
| 알림     | 알림 내역 및 읽음 상태                                                            | 알림 발생의 원인이 된 도메인 사건 (이벤트를 발행한 각 컨텍스트)                                               |

### 컨텍스트로 두지 않는 영역

특정 비즈니스 도메인의 고유 규칙이 아니거나 여러 컨텍스트의 결과를 조합하기만 하는 기능은 별도의 바운디드 컨텍스트로 두지 않습니다.

| 항목                                                   | 처리 방식                                                                                                       |
| ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------- |
| 블로그 대시보드                                        | 분석(방문 통계, 인기 글 ID)과 출판(글 제목·슬러그)의 조회 결과를 진입점 계층에서 화면 모델로 조합합니다.        |
| 관리자 대시보드 및 관리 기능                           | 별도의 진입점으로 구성하여 회원, 출판, 분석 컨텍스트의 공개 기능을 호출합니다 ([배경 참고](#관리자-역할-분리)). |
| HTTP 요청 인증 처리                                    | 진입점의 기술적 관심사입니다 (단, 토큰 발급 및 자격증명 검증 규칙 자체는 회원 컨텍스트에 속합니다).             |
| 공통 기술 기반 (식별자 생성, 공통 예외, 영속성 베이스) | 공유 커널에 두며, 특정 비즈니스 도메인 개념은 포함하지 않습니다.                                                |

### 보류 항목

현재 단계에서는 확정하지 않고 관련 기능이 도입될 때 결정할 도메인 정책입니다.

| 항목                                                                     | 결정 예정 시점        |
| ------------------------------------------------------------------------ | --------------------- |
| 정지되거나 탈퇴한 회원의 기존 블로그와 게시글을 독자에게 어떻게 노출할지 | 관리자 기능 구현 시점 |

## 설계 배경

### 도메인 단위 컨텍스트 구성

과거 레거시 구조에서는 계정, 프로필, 블로그, 글, 댓글, 미디어, 영상, 구독, 알림을 각각 별도의 컨텍스트로 나누어 컨텍스트당 애그리거트를 하나씩만 두었습니다. 그러나 이처럼 지나치게 잘게 나눈 구조에서는 다음과 같은 문제가 발생했습니다.

- 블로그, 카테고리, 게시글이 서로의 서비스를 양방향으로 참조하는 순환 의존이 발생했습니다.
- 블로그 개설(블로그 + 기본 카테고리 + 샘플 글 생성)처럼 즉시 일관성이 보장되어야 하는 단일 유스케이스가 여러 컨텍스트에 걸친 분산 트랜잭션 형태가 되었습니다.
- 화면 표시용 회원 정보(이름, 사진)가 계정의 민감 정보(이메일, 권한)와 분리되지 않은 채 다른 영역 전반으로 확산되었습니다.

이를 해결하기 위해 애그리거트 1:1 분할 방식을 폐기하고, 언어의 일관성과 생명주기를 공유하는 도메인 단위로 바운디드 컨텍스트를 재구성했습니다.

### 회원 컨텍스트의 애그리거트 분리

과거에는 조회 패턴과 보안 민감도가 다르다는 이유로 계정(`Account`)과 프로필(`Profile`)을 별도 컨텍스트로 분리했습니다.

| 구분              | 계정 (`Account`)                  | 프로필 (`Profile`)                               |
| ----------------- | --------------------------------- | ------------------------------------------------ |
| 포함 정보         | 이메일, 계정 상태, 자격증명, 권한 | 표시 이름, 프로필 사진                           |
| 보안 민감도       | 높음 (비공개)                     | 낮음 (전체 공개)                                 |
| 조회 시점 및 빈도 | 인증·로그인 및 계정 설정 시       | 게시글·댓글 화면을 렌더링할 때마다 빈번하게 조회 |
| 조회 주체         | 계정 본인                         | 모든 독자 및 회원                                |

그러나 두 개념 모두 '회원' 한 사람을 구성하는 요소이며, 회원가입 시 계정과 기본 프로필이 즉시 함께 생성되어야 하고 회원 탈퇴 시 동일한 생명주기에 따라 정리됩니다. 따라서 위 표의 차이는 컨텍스트를 나눌 이유가 아니라 **같은 회원 컨텍스트 안에서 애그리거트를 분리할 이유**에 해당합니다. 외부 컨텍스트에는 프로필 조회 계약만 공개하고 계정 모델은 노출하지 않음으로써 보안 민감도 차이와 정보 확산 문제를 함께 해결합니다.

### 출판 컨텍스트 통합

블로그, 카테고리, 게시글은 동일한 행위자(블로거)가 자신의 블로그를 운영하고 글을 발행한다는 동일한 목적으로 변경합니다.

- 블로그 개설 시 샘플 카테고리와 샘플 게시글이 단일 트랜잭션 안에서 즉시 함께 생성되어야 합니다.
- 카테고리를 삭제할 때는 해당 카테고리에 속한 게시글 유무를 확인해야 하고, 게시글을 작성할 때는 지정한 카테고리가 동일한 블로그 소속인지 검증해야 합니다.
- 1인 블로그 전제에 따라 게시글의 작성자는 곧 블로그 소유자이므로, 블로그와 게시글이 '작성자'라는 개념을 직접 공유합니다.

따라서 세 애그리거트를 하나의 출판 컨텍스트로 통합하여 도메인 불변식을 단일 컨텍스트 내부에서 일관되게 보장합니다.

### 상호작용 컨텍스트 통합

구독, 댓글, 좋아요는 행위 주체가 모두 '로그인한 독자'로 동일하며, 외부 의존 대상 역시 출판(대상 블로그·게시글의 존재 및 공개 여부 확인)과 회원(행위자의 활성 계정 여부 확인)으로 일치합니다. 현재 단계에서는 세 기능 모두 도메인 규칙이 간결하므로 하나의 상호작용 컨텍스트로 묶어 관리하며, 추후 댓글 신고·중재처럼 특정 기능의 규칙이 독자적으로 복잡해지는 시점에 분리를 검토합니다.

### 조회수 소유권 분리

조회수는 게시글 화면에 표시되지만 출판이 아닌 **분석 컨텍스트**가 소유합니다.

- 무엇을 유효한 조회 1회로 인정할지(예: 동일 독자의 30분 이내 재방문 및 블로그 소유자 본인 방문 제외)는 분석 도메인의 규칙이며, 출판 컨텍스트의 도메인 규칙 중 조회수에 의존하는 규칙은 없습니다.
- 조회는 독자가 글을 읽을 때마다 발생하는 고빈도 이벤트입니다. 이를 게시글 엔티티의 상태 변경으로 처리하면 독자의 읽기(Read) 행위가 출판 도메인의 쓰기(Write) 경합을 유발합니다.
- 플랫폼 전체 통계를 다루는 관리자 대시보드는 개별 블로그 경계를 넘어 데이터를 집계하므로, 분석 컨텍스트가 통합 소유해야 한 곳에서 일관되게 처리할 수 있습니다.

### 좋아요 수 소유권 분리

좋아요는 단순 로그 집계가 아니라 로그인한 회원의 명시적인 도메인 행위입니다. "한 회원이 한 게시글에 한 번만 남길 수 있고, 취소할 수 있다"는 불변식을 상호작용 컨텍스트가 검증하므로, 그 결과인 좋아요 수 역시 출판이 아닌 **상호작용 컨텍스트**가 소유합니다.

### 미디어 컨텍스트 단일화

영상의 업로드 요청 처리, HLS 스트리밍 인코딩, 미사용 파일 정리는 서로 다른 실행 프로세스에서 동작합니다. 그러나 세 작업 모두 동일한 영상 상태 전이 규칙(`VideoStatus`)을 공유합니다. 물리적 실행 단위와 논리적 도메인 경계는 별개의 축이므로, 미디어 상태 규칙은 하나의 미디어 컨텍스트 안에 응집시킵니다.

### 관리자 역할 분리

관리자는 새로운 비즈니스 도메인이 아니라 기존 컨텍스트의 기능을 호출하는 운영 행위자(Actor)입니다.

| 관리자 기능             | 실제 규칙을 수행하는 컨텍스트 |
| ----------------------- | ----------------------------- |
| 블로거 계정 정지 처리   | 회원                          |
| 게시글 비공개·숨김 처리 | 출판                          |
| 플랫폼 전체 통계 조회   | 분석                          |

따라서 별도의 관리자 컨텍스트를 두지 않고 각 컨텍스트가 공개한 기능을 조합해 호출합니다. 추후 신고 접수, 제재 이력, 이의 신청 절차처럼 독자적인 운영 도메인 규칙과 상태 모델이 도입될 때 운영(Moderation) 컨텍스트를 신설합니다.
