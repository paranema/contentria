# 회원 규칙

계정을 만들고, 로그인하고, 인증 수단을 붙이고 떼는 규칙과 프로필 규칙이다.

각 흐름은 위에서부터 **처음 걸리는 줄**에서 멈춘다.
`계층` 열이 `도메인`인 줄이 도메인 불변식이고, `앱`인 줄이 애플리케이션 정책이다.
분류 기준은 [02-implementation.md](02-implementation.md)에 있다.

## 전제

1. 계정 하나에 자격증명 여러 개가 붙는다.
2. 계정에 저장된 이메일은 **항상 확인된 주소다.** 미확인 주소가 계정에 들어가는 경로는 없다.
3. 이메일은 계정의 속성이다. 자격증명은 이메일을 저장하지 않는다.
4. 소셜 신원 판단은 **공급자 사용자 ID로만** 한다. 이메일로 하지 않는다.
5. 이메일은 계정을 합칠지 판단할 때만 쓴다.
6. 공급자는 이메일 확인 정책을 검토한 뒤 신뢰 목록에 넣는다.

## 계정 상태

| 상태 | 로그인 | 글·댓글 | 계층 |
|---|---|---|---|
| ACTIVE | 가능 | 가능 | 도메인 |
| SUSPENDED | 불가 | 불가 | 도메인 |
| DELETED | 불가 | 불가 | 도메인 |

## 흐름 1. 로컬 회원가입

`이메일 입력 → 코드 발송 → 코드 확인 → 비밀번호 설정 → 계정 생성`

| # | 조건 | 처리 | 계층 |
|---|---|---|---|
| 1 | 같은 이메일 계정 있음 | 거부 (409) | 앱 + DB |
| 2 | 없음 | 가입 시도 생성, 코드 발송. **계정은 만들지 않음** | 앱 |
| 3 | 코드 확인 성공 | 같은 세션에서 비밀번호를 받아 계정(ACTIVE)과 로컬 자격증명 생성 | 앱 → 도메인 |

### 가입 시도

| 항목 | 규칙 | 계층 |
|---|---|---|
| 담는 것 | 이메일, 코드 해시, 시도 횟수, 만료 시각 | 앱 |
| 담지 않는 것 | **비밀번호를 포함한 모든 사용자 입력값** ([왜](#가입-시도에-사용자-입력을-담지-않는다)) | 앱 |
| 만료 | 10분 | 어댑터 |
| 시도 횟수 | 5회 실패 시 무효화, 재발송 요구 | 앱 |
| 재발송 | 이전 코드 즉시 무효화 | 앱 |
| 검증 범위 | 코드를 요청한 세션에서만 | 앱 |
| 코드 생성·저장 | 암호학적 난수, 해시로 저장 | 어댑터 |

## 흐름 2. 소셜 로그인 (가입 겸용)

| # | 조건 | 처리 | 계층 |
|---|---|---|---|
| 1 | ID 토큰 서명 검증 실패 | 거부 | 어댑터 |
| 2 | `(공급자, 사용자ID)` 자격증명 있음 | ACTIVE면 로그인, 아니면 거부 ([왜](#2번에서-email_verified를-보지-않는다)) | 앱 → 도메인 |
| 3 | 이메일 클레임 없음 | 거부. 공급자 화면에서 동의하도록 안내 | 앱 |
| 4 | `email_verified`가 `true`가 아님 | 거부. "로그인 후 설정에서 연동하세요" | 도메인 |
| 5 | 같은 이메일 계정 없음 | 계정(ACTIVE)과 자격증명 생성, 로그인 | 앱 → 도메인 |
| 6 | 같은 이메일 계정이 ACTIVE 아님 | 거부 ([왜](#정지된-계정을-대체하지-않는다)) | 앱 → 도메인 |
| 7 | 같은 이메일 계정이 ACTIVE | 자동 연동 후 로그인, 안내 메일 | 앱 → 도메인 + 이벤트 |

클레임이 아예 없으면 `false`로 취급한다. 값은 서명이 검증된 ID 토큰에서 불리언으로 파싱해 읽는다.

## 흐름 3. 수동 연동 (설정 화면)

**로그인된 상태에서만 시작한다. 이 흐름은 계정을 만들지 않는다.**
소셜 로그인과 같은 콜백으로 돌아오므로 요청에 의도를 실어 보내고 콜백에서 구분한다.

| # | 조건 | 처리 | 계층 |
|---|---|---|---|
| 1 | 그 소셜 신원이 타 계정 소유 | 실패. 계정을 합치지 않는다 | 앱 + DB |
| 2 | 현재 계정에 그 공급자가 이미 있음 | 실패 | 도메인 |
| 3 | 그 외 | 추가. 계정 이메일은 바뀌지 않음 | 도메인 |

`email_verified`를 보지 않는다. 로그인 상태이고 공급자 인증도 통과했으므로 양쪽 통제권이 이미 증명되었다.

## 흐름 4. 계정 관리

| 항목 | 규칙 | 계층 |
|---|---|---|
| 비밀번호 최초 설정 (소셜 전용 계정) | 계정 이메일로 설정 링크. 링크를 통해서만 | 앱 → 도메인 |
| 비밀번호 변경 | 현재 비밀번호 확인 후 변경 | 앱 → 도메인 |
| 비밀번호 분실 | 계정 이메일로 재설정 링크 | 앱 |
| 연동 해제 | 해제 전 자격증명이 1개면 불가 | 도메인 |
| 이메일 변경 | 새 주소 확인 + 기존 주소 알림. 확인 전까지 미반영 ([왜](#이메일-변경에-확인이-필요하다)) | 앱 → 도메인 |
| 탈퇴 (ACTIVE) | DELETED로 바꾸고 **이메일 익명화 + 자격증명 전부 삭제** ([왜](#탈퇴는-이메일과-신원을-놓아준다)). 프로필은 지우지 않고 탈퇴 표시만 남긴다 | 도메인 |
| 탈퇴 (SUSPENDED) | 불가. 문의로 처리 | 앱 |

설정 링크와 재설정 링크의 토큰은 1회용이고, 만료가 있고, 계정에 묶인다.

## 흐름 5. 프로필

프로필은 다른 사람에게 보이는 표시 이름과 사진이다. 블로그가 여러 개여도 회원당 하나다.

이 절은 현재 구현에서 옮겨 적었다. 제품 규칙으로 검토를 거치지 않았다.

| 항목 | 규칙 | 계층 |
|---|---|---|
| 생성 | 계정을 만들 때 함께 만든다. 계정당 하나 | 앱 → 도메인 |
| 표시 이름 길이 | 앞뒤 공백을 제거한 뒤 2자 이상 50자 이하 | 도메인 |
| 표시 이름 중복 | 불가 | 앱 + DB |
| 표시 이름 자동 생성 | 가입할 때 항상 `형용사_명사_네 자리 숫자` 형식으로 만든다. 소셜 공급자가 준 이름은 실명이므로 쓰지 않는다. 이미 쓰이는 이름이면 다시 만든다 | 앱 |
| 탈퇴한 회원의 프로필 | 지우지 않고 탈퇴 표시만 남긴다. 표시 이름과 사진도 남긴다. 화면에 어떻게 보일지는 화면 조합에서 정한다 | 도메인 |
| 표시 이름 변경 | 본인만. 길이와 중복 규칙은 생성과 같다 | 앱 → 도메인 |
| 사진 | 값이 없거나 빈 문자열이면 사진 없음으로 둔다. 주소가 2048자를 넘으면 거부한다 | 도메인 |
| 공개 범위 | 누구나 조회한다. 이메일, 계정 상태, 권한을 담지 않는다 | 앱 |

가입 화면에서 표시 이름을 받지 않는 이유는 [가입 시도에 사용자 입력을 담지 않는다](#가입-시도에-사용자-입력을-담지-않는다)에 있다.

## 흐름 6. 이메일 코드 로그인

비밀번호 대신 계정 이메일로 받은 코드로 로그인한다. 비밀번호가 있는 계정도 쓸 수 있다.

| # | 조건 | 처리 | 계층 |
|---|---|---|---|
| 1 | 같은 이메일의 계정이 없음 | 코드를 보내지 않는다. 응답은 2번과 같다 ([왜](#코드-로그인은-계정-존재를-알려주지-않는다)) | 앱 |
| 2 | 계정이 있음 | 로그인 시도를 만들고 코드를 보낸다 | 앱 |
| 3 | 코드 확인 성공 | 계정이 ACTIVE면 세션을 시작한다. 아니면 거부 | 앱 → 도메인 |

로그인 시도는 가입 시도와 같은 규칙을 따른다. 만료 10분, 5회 실패 시 무효화, 재발송 시 이전 코드 무효화, 코드를 요청한 세션에서만 검증, 코드는 해시로 저장.

## 공통

| 항목 | 규칙 | 계층 |
|---|---|---|
| 세션 무효화 | 비밀번호 설정·변경·재설정, 연동 해제, 이메일 변경 확정, 정지, 탈퇴 시 다른 세션 전부 | 앱 |
| 속도 제한 | **실패한 요청도 한도를 소비한다.** IP만이 아니라 계정·이메일도 키에 넣는다 | 어댑터 |
| 로그인 실패 응답 | 미가입인지 비밀번호 오류인지 구분하지 않는다 | 앱 |
| 가입 시 중복 응답 | 409로 알린다. 어떤 공급자로 가입됐는지도 알려준다 | 앱 |
| 이메일 정규화 | 앞뒤 공백 제거 + 소문자. **점이나 `+` 이후는 제거하지 않는다** | 도메인 |

비밀번호 해싱, 토큰 수명, 쿠키 속성은 [conventions/security.md](../../conventions/security.md)를 따른다.

## 왜 이렇게 정했나

다시 읽는 사람이 스스로 도출하기 어려운 것만 적는다.

### 가입 시도에 사용자 입력을 담지 않는다

담으면 이 공격이 성립한다.

1. 피해자가 가입을 시작한다. 코드 A가 피해자 메일함에 도착한다.
2. 공격자가 같은 이메일로 가입을 시작한다. 코드 B가 같은 메일함에 도착한다.
3. 피해자가 방금 온 메일을 열고 코드 B를 입력한다.
4. 공격자가 정한 비밀번호가 담긴 시도가 계정이 된다.

같은 이메일의 시도들이 코드 값 말고 전부 동일하면 어느 것이 확인되든 결과가 같다.
"가입 화면에서 닉네임도 받자" 같은 변경은 이 공격을 되살린다.

### 2번에서 `email_verified`를 보지 않는다

자격증명이 있다는 것은 과거에 `true`인 상태로 가입 또는 연동이 일어났다는 뜻이다.
로그인은 공급자 사용자 ID로 하므로 이메일은 판단 재료가 아니다.

여기서 확인하면, 공급자 쪽에서 이메일을 바꾸고 확인하지 않은 사용자가 자기 계정에서 영구히 잠긴다.
가입 후 공급자 쪽 이메일 변경은 계정에 반영하지 않는다.

### 정지된 계정을 대체하지 않는다

새 계정을 만들면 정지된 사용자가 소셜 로그인만으로 깨끗한 계정을 얻는다.
기존 계정을 지우면 제재 기록까지 사라져 관리자가 확인할 수 없다.

미확인 계정 대체와 혼동하기 쉽다. 미확인은 아무도 소유를 증명하지 않은 상태이고,
정지는 소유자가 확정된 계정에 제재가 걸린 상태다.

### 이메일 변경에 확인이 필요하다

계정 이메일은 자동 연동의 판단 기준이다. 확인 없이 바꾸면, 공격자가 자기 계정 이메일을
피해자 주소로 바꿔두고 피해자의 소셜 로그인을 흡수할 수 있다.

기존 주소로도 알리는 이유는, 계정을 가져간 뒤 이메일부터 바꾸는 것이 전형적인 순서이기 때문이다.

### 탈퇴는 이메일과 신원을 놓아준다

상태만 바꾸면 이메일과 소셜 식별자가 계속 점유되어 같은 주소로 다시 가입할 수 없다.

### 코드 로그인은 계정 존재를 알려주지 않는다

코드 요청에 "가입되지 않은 주소"라고 답하면, 누구나 주소를 넣어 보며 가입 여부를 알아낼 수 있다.
가입 시 중복을 409로 알리는 것(공통 규칙)과 다른 이유는, 가입은 그 주소로 계정을 만들려는 사람에게 다음 행동(로그인)을 알려줘야 하지만 로그인 코드 요청은 그럴 필요가 없기 때문이다.

## 보류

| 항목 | 사유 |
|---|---|
| 계정 합치기 | 양쪽의 글과 댓글을 옮기고 충돌을 해소해야 한다. 얻는 것은 소수의 편의다 |
| 공급자 측 연결 해제 웹훅 | 초기 단계에서 다루지 않는다 |

계정이 둘로 나뉘는 상황 자체를 줄이는 쪽이 효과가 크다.
로그인 화면에 마지막 사용 수단을 표시하고, 새 계정 생성을 사용자가 알아채게 한다.

## 확인 필요

공급자 문서로 확인해야 한다.

| 공급자 | 질문 |
|---|---|
| 애플 | 첫 인증 이후에도 이메일 클레임이 오는가. 오지 않으면 흐름 2의 3번이 두 번째 로그인부터 걸린다 |
| 애플 | 탈퇴 시 토큰 회수가 요구사항인가 |
| 애플 | 비공개 이메일 사용자는 자동 연동이 일어나지 않는다. 의도한 동작인가 |
| 네이버, 카카오 | 이메일을 필수 동의로 설정할 수 있는가 |
| 네이버, 카카오 | `email_verified`에 해당하는 값을 주는가. 주지 않으면 자동 연동에서 제외한다 |
