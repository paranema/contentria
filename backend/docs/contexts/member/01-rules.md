# 회원 도메인 규칙

계정을 생성하고 로그인하며, 인증 수단(자격증명)을 연동·해제하고 프로필을 관리하는 비즈니스 규칙을 정의합니다.

## 전제 조건

1. 하나의 계정(`Account`)에 여러 개의 자격증명(`Credential`)을 연결할 수 있습니다.
2. 계정에 저장된 이메일 주소는 **항상 소유권 검증이 완료된 이메일**입니다. 미인증 이메일이 계정 테이블에 저장되는 경로는 없습니다.
3. 이메일은 계정의 고유 속성이며, 개별 자격증명은 이메일을 중복 저장하지 않습니다.
4. 소셜 로그인 시 사용자 식별은 이메일이 아닌 **`(소셜 공급자, 공급자 측 사용자 ID)` 조합으로만** 판단합니다.
5. 소셜 공급자가 반환한 이메일 주소는 기존 계정과의 자동 연동 여부를 판단할 때만 사용합니다.
6. 소셜 공급자는 이메일 검증 정책이 확인된 공급자만 신뢰 목록에 등록해 지원합니다.

## 계정 상태 (`AccountStatus`)

| 상태        | 로그인 허용 | 게시글·댓글 작성 | 검증 계층 |
| ----------- | ----------- | ---------------- | --------- |
| `ACTIVE`    | 가능        | 가능             | 도메인    |
| `SUSPENDED` | 불가        | 불가             | 도메인    |
| `DELETED`   | 불가        | 불가             | 도메인    |

## 주요 비즈니스 흐름

회원 컨텍스트의 동작은 **이메일·소셜 회원가입 및 로그인(흐름 1, 2, 6), 소셜 계정 수동 연동(흐름 3), 계정 보안 설정 및 탈퇴(흐름 4), 공개 프로필 관리(흐름 5)**의 여섯 가지 흐름으로 구성됩니다.

- 각 흐름의 조건 표는 위에서부터 순서대로 평가하며 **처음 일치하는 조건**에서 처리를 멈춥니다.
- `검증 계층`(`담당 계층`) 열이 `도메인`으로 표기된 항목은 도메인 엔티티가 보장하는 불변식이고, `앱`으로 표기된 항목은 응용 서비스가 조율하는 애플리케이션 정책입니다.
  - 분류 기준은 [02-implementation.md](02-implementation.md) 참고

### 흐름 1. 이메일 회원가입

`이메일 입력 → 인증 코드 발송 → 인증 코드 검증 → 비밀번호 설정 → 계정 생성` 순서로 진행됩니다.

| # | 조건                               | 처리 내용                                                                                  | 검증 계층    |
| - | ---------------------------------- | ------------------------------------------------------------------------------------------ | ------------ |
| 1 | 동일 이메일로 가입된 계정이 존재함 | 가입 요청을 거부합니다 (`409 Conflict`).                                                   | 앱 + DB      |
| 2 | 가입된 계정이 없음                 | 가입 시도(`SignUpAttempt`)를 생성하고 인증 코드를 발송합니다 (**아직 계정은 생성하지 않음**). | 앱           |
| 3 | 인증 코드 검증 성공                | 동일 세션에서 비밀번호를 입력받아 활성(`ACTIVE`) 계정과 이메일 자격증명을 생성합니다.      | 앱 → 도메인  |

#### 가입 시도 (`SignUpAttempt`) 관리 규칙

| 항목           | 규칙                                                                                                 | 담당 계층 |
| -------------- | ---------------------------------------------------------------------------------------------------- | --------- |
| 저장하는 정보  | 대상 이메일, 인증 코드 해시, 검증 실패 횟수, 만료 시각                                               | 앱        |
| 저장 금지 정보 | **비밀번호 및 닉네임을 포함한 모든 사용자 입력값** ([이유 참고](#가입-시도에-사용자-입력을-담지-않는다)) | 앱        |
| 유효 시간      | 발급 후 10분                                                                                         | 어댑터    |
| 실패 횟수 제한 | 5회 검증 실패 시 해당 시도를 즉시 무효화하고 코드 재발송을 요구합니다.                               | 앱        |
| 코드 재발송    | 새 코드를 발송하면 이전에 발급된 코드는 즉시 무효화됩니다.                                           | 앱        |
| 검증 범위      | 가입 시도를 시작한 세션(시도 ID 보유자)에서만 코드를 검증할 수 있습니다.                             | 앱        |
| 코드 생성·보관 | 암호학적 난수로 생성하며 원문 대신 해시값만 저장합니다.                                              | 어댑터    |

### 흐름 2. 소셜 로그인 (회원가입 겸용)

| # | 조건                                              | 처리 내용                                                                                   | 검증 계층            |
| - | ------------------------------------------------- | ------------------------------------------------------------------------------------------- | -------------------- |
| 1 | ID 토큰 서명 검증 실패                            | 요청을 거부합니다.                                                                          | 어댑터               |
| 2 | `(공급자, 공급자 사용자 ID)` 자격증명이 이미 존재 | 연결된 계정이 `ACTIVE`이면 로그인을 허용하고, 아니면 거부합니다 ([이유 참고](#2번에서-email_verified를-보지-않는다)). | 앱 → 도메인          |
| 3 | ID 토큰에 이메일 클레임이 없음                    | 요청을 거부하고 소셜 공급자 동의 화면에서 이메일 제공에 동의하도록 안내합니다.              | 앱                   |
| 4 | `email_verified` 클레임이 `true`가 아님           | 요청을 거부합니다 ("기존 계정으로 로그인한 뒤 계정 설정에서 연동해 주세요").                | 도메인               |
| 5 | 동일 이메일을 사용하는 기존 계정이 없음           | 신규 계정(`ACTIVE`)과 소셜 자격증명을 생성하고 로그인 처리합니다.                           | 앱 → 도메인          |
| 6 | 동일 이메일 계정이 존재하나 `ACTIVE` 상태가 아님  | 요청을 거부합니다 ([이유 참고](#정지된-계정을-대체하지-않는다)).                            | 앱 → 도메인          |
| 7 | 동일 이메일 계정이 존재하고 `ACTIVE` 상태임       | 기존 계정에 소셜 자격증명을 자동 연동한 뒤 로그인 처리하고 안내 메일을 발송합니다.          | 앱 → 도메인 + 이벤트 |

- `email_verified` 클레임이 누락된 경우에는 `false`로 간주하며, 서명이 검증된 ID 토큰에서 불리언 타입으로 파싱해 확인합니다.

### 흐름 3. 소셜 계정 수동 연동 (계정 설정 화면)

**이미 로그인된 상태에서만 시작할 수 있으며, 이 흐름에서는 신규 계정을 생성하지 않습니다.**
소셜 로그인과 동일한 OAuth 콜백 URL을 공유하므로, 인가 요청 시작 시 연동 의도(`intent=link`)를 함께 기록하고 콜백 시점에 이를 구분합니다.

| # | 조건                                              | 처리 내용                                                             | 검증 계층 |
| - | ------------------------------------------------- | --------------------------------------------------------------------- | --------- |
| 1 | 해당 소셜 신원이 이미 다른 계정에 연동되어 있음   | 연동을 거부합니다 (서로 다른 두 계정을 병합하지 않음).                | 앱 + DB   |
| 2 | 현재 계정에 동일한 소셜 공급자가 이미 연동되어 있음| 연동을 거부합니다.                                                    | 도메인    |
| 3 | 위 조건에 모두 해당하지 않음                      | 현재 계정에 소셜 자격증명을 추가합니다 (계정의 대표 이메일은 유지됨). | 도메인    |

- 수동 연동 시에는 소셜 토큰의 `email_verified` 여부를 검사하지 않습니다. 이미 로그인을 통해 현재 계정의 소유권이 확인되었고 소셜 공급자 인증도 통과했으므로 양쪽 신원에 대한 통제권이 모두 증명되었기 때문입니다.

### 흐름 4. 계정 관리 및 보안 설정

| 기능 항목                         | 처리 규칙                                                                                                                                                                                             | 검증 계층   |
| --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 비밀번호 최초 설정 (소셜 전용 계정)| 계정 이메일로 발송된 설정 링크를 통해서만 비밀번호를 생성할 수 있습니다.                                                                                                                               | 앱 → 도메인 |
| 비밀번호 변경                     | 현재 비밀번호가 일치하는지 확인한 뒤 새 비밀번호로 변경합니다.                                                                                                                                         | 앱 → 도메인 |
| 비밀번호 분실 재설정              | 입력한 계정 이메일로 비밀번호 재설정 링크를 발송합니다.                                                                                                                                                | 앱          |
| 소셜 연동 해제                    | 연동 해제 후 남는 자격증명이 0개가 되는 경우(유일한 로그인 수단인 경우)에는 해제를 거부합니다.                                                                                                         | 도메인      |
| 이메일 주소 변경                  | 현재 이메일과 새 이메일로 각각 발송된 두 인증 코드를 모두 검증해야 변경이 확정됩니다. 확정 시 기존 이메일 주소로 변경 알림 메일을 발송합니다 ([이유 1](#이메일-변경에-확인이-필요하다), [이유 2](#이메일-변경과-탈퇴는-현재-주소로-다시-확인한다)). | 앱 → 도메인 |
| 회원 탈퇴 (`ACTIVE` 계정)         | 현재 계정 이메일로 발송된 인증 코드를 검증해 확정합니다 ([이유 참고](#이메일-변경과-탈퇴는-현재-주소로-다시-확인한다)). 확정 시 계정 상태를 `DELETED`로 전환하고 **이메일 익명화 및 모든 자격증명 삭제**를 수행합니다 ([이유 참고](#탈퇴는-이메일과-신원을-놓아준다)). 프로필은 삭제하지 않고 탈퇴 표시만 남깁니다. | 도메인      |
| 회원 탈퇴 (`SUSPENDED` 계정)      | 정지된 계정은 직접 탈퇴할 수 없으며 고객 문의를 통해 처리합니다.                                                                                                                                      | 앱          |

- 비밀번호 설정 링크 및 재설정 링크에 사용되는 토큰은 특정 계정에 귀속되며, 만료 시간이 존재하는 1회용 토큰입니다.

### 흐름 5. 프로필 (`Profile`)

프로필은 다른 사용자에게 공개되는 표시 이름(`displayName`)과 프로필 사진이며, 한 회원이 여러 블로그를 운영하더라도 회원당 하나만 존재합니다.

| 항목                 | 규칙                                                                                                                                                              | 검증 계층   |
| -------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 프로필 생성          | 회원가입 시 계정 생성과 함께 1:1로 생성됩니다.                                                                                                                    | 앱 → 도메인 |
| 표시 이름 길이       | 앞뒤 공백을 제거한 기준 2자 이상 50자 이하만 허용합니다.                                                                                                          | 도메인      |
| 표시 이름 중복       | 플랫폼 전체에서 중복될 수 없습니다.                                                                                                                               | 앱 + DB     |
| 초기 표시 이름 생성  | 가입 시 항상 `형용사_명사_4자리숫자` 형식으로 자동 생성합니다. 소셜 공급자가 제공한 이름은 실명 노출 우려가 있어 사용하지 않으며, 중복 발생 시 재생성합니다.      | 앱          |
| 표시 이름 변경       | 계정 본인만 변경할 수 있으며, 길이 및 중복 금지 규칙은 최초 생성 시와 동일합니다.                                                                                 | 앱 → 도메인 |
| 프로필 사진          | 값이 없거나 빈 문자열이면 기본 상태(사진 없음)로 두며, 이미지 URL 길이가 2048자를 초과하면 거부합니다.                                                            | 도메인      |
| 탈퇴 회원의 프로필   | 레코드를 삭제하지 않고 표시 이름·사진과 함께 탈퇴 상태 표시만 유지합니다. 화면에서의 구체적인 표기 방식은 화면 조합 계층에서 결정합니다.                          | 도메인      |
| 대외 공개 범위       | 비로그인 독자를 포함한 누구나 조회할 수 있으며, 이메일·계정 상태·권한 등 민감 정보는 절대 포함하지 않습니다.                                                      | 앱          |

- 회원가입 화면에서 표시 이름을 직접 입력받지 않는 보안상의 이유는 [가입 시도에 사용자 입력을 담지 않는다](#가입-시도에-사용자-입력을-담지-않는다) 절에 정리되어 있습니다.

### 흐름 6. 이메일 인증 코드 로그인

비밀번호를 입력하는 대신 계정 이메일로 발송된 1회용 인증 코드로 로그인하는 흐름입니다. 비밀번호가 설정된 일반 계정도 사용할 수 있습니다.

| # | 조건                               | 처리 내용                                                                                                                     | 검증 계층   |
| - | ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------- |
| 1 | 해당 이메일로 가입된 계정이 없음   | 실제로는 메일을 발송하지 않으나, 외부 응답은 2번(성공)과 동일하게 반환합니다 ([이유 참고](#코드-로그인은-계정-존재를-알려주지-않는다)). | 앱          |
| 2 | 가입된 계정이 존재함               | 로그인 시도를 생성하고 해당 이메일로 인증 코드를 발송합니다.                                                                  | 앱          |
| 3 | 인증 코드 검증 성공                | 계정이 `ACTIVE` 상태이면 세션을 발급하고, 정지·탈퇴 상태이면 거부합니다.                                                      | 앱 → 도메인 |

- 로그인 시도의 세부 규칙(유효 시간 10분, 5회 실패 시 무효화, 재발송 시 이전 코드 무효화, 동일 세션 검증, 코드 해시 저장)은 회원가입 시도와 동일합니다.

## 공통 보안 및 인증 규칙

| 항목                 | 규칙                                                                                                                                                      | 담당 계층 |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- |
| 전체 세션 무효화     | 비밀번호 설정·변경·재설정, 소셜 연동 해제, 이메일 변경 확정, 계정 정지, 회원 탈퇴 시 기존에 발급된 다른 기기의 세션을 모두 무효화합니다.                  | 앱        |
| 단일 기기 로그아웃   | 현재 요청을 보낸 브라우저의 세션만 종료하며 다른 기기의 로그인 상태는 유지합니다. 비로그인 상태의 요청에도 동일한 성공 응답을 반환합니다.                 | 앱        |
| 요청 속도 제한       | **인증에 실패한 요청도 제한 한도를 소모합니다.** IP 주소뿐 아니라 계정 식별자와 이메일 주소도 제한 키에 함께 포함합니다.                                  | 어댑터    |
| 로그인 실패 응답     | 미가입 이메일인지 비밀번호 불일치인지 공격자가 구분할 수 없도록 동일한 오류 응답을 반환합니다.                                                            | 앱        |
| 회원가입 중복 응답   | 이미 가입된 이메일로 가입을 시도하면 `409 Conflict`와 함께 가입된 인증 수단(이메일/소셜)을 안내합니다 ([이유 참고](#가입은-가입-여부를-알려준다)).        | 앱        |
| 이메일 주소 정규화   | 앞뒤 공백을 제거하고 영문자를 소문자로 변환합니다 (**로컬 파트의 점(`.`)이나 `+` 뒤 문자열은 임의로 제거하지 않음**).                                     | 도메인    |

- 비밀번호 해싱 방식, JWT 토큰 수명, 세션 쿠키 보안 속성은 [conventions/security.md](../../conventions/security.md)를 따릅니다.

## 봇 방지 (사람 확인)

인증 메일 발송이나 비밀번호 대입을 수행하는 엔드포인트는 자동화 스크립트를 통한 메일 폭주 및 무차별 대입(Brute-force) 공격을 막기 위해 사람 여부(reCAPTCHA)를 먼저 검증합니다.

| # | 조건 및 단계                                                                                 | 처리 내용                                                                      |
| - | -------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| 1 | 검증 대상 요청: 회원가입 시작, 비밀번호 로그인, 코드 로그인 시작, 비밀번호 재설정 링크 요청  | 아래 2~5번 순서로 검증을 수행합니다.                                           |
| 2 | 클라이언트가 체크박스(v2) 검증 토큰을 함께 전송함                                            | v2 토큰만 검증하여 통과 시 요청을 진행하고, 실패 시 요청을 거부합니다.         |
| 3 | 백그라운드(v3) 토큰의 점수가 기준치(`0.5`) 이상이고 요청 동작(`action`) 이름이 일치함        | 정상 사용자로 판단하여 요청을 진행합니다.                                      |
| 4 | 점수가 기준치 미만이거나, 다른 동작용 토큰이거나, 토큰이 누락됨                              | 추가 인증을 요구(`403`)하며, 프론트엔드는 v2 체크박스를 띄워 재요청합니다.     |
| 5 | 외부 검증 공급자(Google)와 통신할 수 없음                                                    | 요청을 진행하지 않고 일시적 장애(`503`)를 반환하여 잠시 후 재시도하게 합니다.  |

- 비밀번호 로그인은 사람 확인을 통과한 뒤에야 비밀번호 일치 여부를 검사하므로, 검증 단계에서 차단된 요청을 통해 계정 존재 여부나 비밀번호 일치 여부를 유추할 수 없습니다.

## 결정과 이유

### 가입 시도에 사용자 입력을 담지 않는다

만약 인증이 완료되기 전의 '가입 시도' 단계에 사용자가 입력한 비밀번호나 표시 이름을 미리 저장해 두면 다음과 같은 세션·계정 탈취 공격이 가능해집니다.

1. 피해자가 자신의 이메일로 가입을 시작하여 피해자의 메일함에 인증 코드 A가 도착합니다.
2. 직후 공격자가 동일한 피해자의 이메일과 **공격자가 지정한 비밀번호**로 가입을 시작하여 피해자의 메일함에 인증 코드 B가 추가로 도착합니다.
3. 피해자가 가장 최근에 도착한 메일을 열어 코드 B를 입력해 인증을 완료합니다.
4. 만약 가입 시도에 공격자의 비밀번호가 담겨 있었다면, 피해자가 인증을 마친 계정에 공격자가 설정한 비밀번호가 등록됩니다.

이를 방지하기 위해 가입 시도 단계에는 오직 이메일과 인증 코드 해시만 기록하고, 비밀번호는 인증 코드 검증이 완료된 세션에서 마지막에 입력받습니다.

### 2번에서 `email_verified`를 보지 않는다

소셜 자격증명이 이미 DB에 존재한다는 것은 최초 가입이나 연동 시점에 이미 검증된 상태로 연결이 완료되었음을 의미합니다. 이후 재로그인 시에는 공급자 사용자 ID(`sub`)로만 계정을 식별하므로 이메일은 식별 기준이 아닙니다.

만약 재로그인 때마다 `email_verified`를 다시 검사하면, 소셜 공급자 측에서 이메일을 변경한 뒤 아직 재인증을 마치지 않은 사용자가 기존 Contentria 계정에서 영구적으로 잠기게 됩니다.

### 정지된 계정을 대체하지 않는다

소셜 로그인 시 동일한 이메일을 가진 기존 계정이 정지(`SUSPENDED`) 상태일 때 이를 무시하고 새 계정을 만들어 주면, 제재를 받은 사용자가 소셜 로그인만으로 손쉽게 제재를 우회할 수 있습니다. 또한 기존 계정을 덮어쓰면 관리자가 제재 이력을 추적할 수 없게 되므로 로그인을 거부합니다.

### 이메일 변경에 확인이 필요하다

계정의 이메일 주소는 소셜 로그인 시 자동 연동 여부를 결정하는 기준입니다. 만약 소유권 검증 없이 이메일을 바꿀 수 있다면, 공격자가 자신의 계정 이메일을 피해자의 이메일 주소로 변경해 둔 뒤 피해자가 소셜 로그인을 시도할 때 피해자의 소셜 신원을 공격자 계정으로 흡수할 수 있습니다.
또한 계정 탈취 직후 공격자가 가장 먼저 시도하는 행위가 이메일 변경이므로, 변경 확정 시 기존 이메일 주소로도 알림 메일을 발송합니다.

### 이메일 변경과 탈퇴는 현재 주소로 다시 확인한다

로그인된 세션 쿠키만으로 이메일 변경이나 회원 탈퇴를 즉시 허용하면, XSS나 공용 PC 방치 등으로 세션을 탈취한 공격자가 이메일을 자신의 주소로 바꾼 뒤 비밀번호를 재설정해 계정을 완전히 빼앗을 수 있습니다.
따라서 이메일 변경과 되돌릴 수 없는 회원 탈퇴는 현재 등록된 이메일 주소로 발송된 인증 코드를 다시 확인하는 재인증 절차를 거칩니다(비밀번호가 없는 소셜 전용 계정도 동일하게 이용할 수 있도록 이메일 코드로 검증합니다).

### 탈퇴는 이메일과 신원을 놓아준다

회원 탈퇴 시 계정 상태만 `DELETED`로 바꾸고 이메일과 소셜 식별자를 그대로 남겨두면, 고유 제약 조건 때문에 사용자가 추후 동일한 이메일이나 소셜 계정으로 재가입할 수 없게 됩니다. 따라서 탈퇴 확정 시 이메일을 익명화하고 자격증명 레코드를 모두 삭제합니다.

### 가입은 가입 여부를 알려준다

회원가입 시작 시 이미 사용 중인 이메일이면 `409 Conflict`와 함께 가입된 인증 수단을 알려줍니다. 이는 공격자가 특정 이메일의 가입 여부를 확인할 수 있는 경로(User Enumeration)가 되지만, 실제 사용자가 자신이 과거에 어떤 방식으로 가입했는지 몰라 겪는 불편을 줄이기 위해 의도적으로 선택한 트레이드오프입니다.

만약 추후 보안 요구사항이 강화되어 가입 여부를 완전히 숨겨야 한다면, 가입 시작 요청에 항상 `202 Accepted`를 반환하고 이미 가입된 주소로는 인증 코드 대신 '이미 가입된 계정 안내' 메일을 발송하는 방식으로 전환합니다.

### 코드 로그인은 계정 존재를 알려주지 않는다

회원가입과 달리 이메일 코드 로그인 요청에서는 미가입 이메일이 입력되더라도 가입된 계정과 동일한 성공 응답을 반환합니다. 코드 로그인 단계에서 굳이 계정 존재 여부를 노출해 이메일 열거 공격 경로를 하나 더 늘릴 필요가 없기 때문입니다.
